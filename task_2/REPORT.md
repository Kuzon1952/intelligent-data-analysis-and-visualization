# Отчёт по заданию 2 · Можно ли доверять модели-советчику SOC

> Файл собран скриптом `task_2/report.py` из тех же функций, что и дашборд. Порог модели — 0,18 (в `model_params` записан порог 0,82 для класса «FP», то есть тревога поднимается при оценке вероятности инцидента ≥ 0,18).

## Что за данные

`MODEL_PREDICTIONS_target.parquet` — лог работы модели в режиме советчика: 19 393 прогонов с 04.09.2025 по 20.11.2025. Для каждой карточки есть оценка модели (`y_pred_proba`), её решение (`y_pred`) и итоговый вердикт аналитика (`y`: 1 — инцидент, 0 — ложное срабатывание). В метрики входят только размеченные карточки — **15 839**; без разметки 2 950, спам и дубликаты 604 исключены, иначе precision и recall были бы искажены.

## Кому и зачем

Зритель — **руководство SOC**, не специалисты по машинному обучению. Поэтому на дашборде нет AUC и F1: все метрики сформулированы как ответы на вопросы руководителя — «сколько инцидентов мы потеряем», «сколько работы модель снимет», «где ей нельзя верить». Главная метрика по условию задания — **доля пропущенных реальных инцидентов**, ей отдана красная плитка и красная клетка матрицы.

## Ответ на главный вопрос

**Как советчику, который сортирует очередь, — доверять можно; как фильтру, после которого карточки не смотрят, — нельзя.** При пороге 0,18 модель отдаёт аналитикам 25 % карточек и ловит 79,9 % реальных инцидентов, но **пропускает 335 из 1 666 (20,1 %)**. В «спокойной» стопке (75 % карточек) каждая ≈ 36-я — реальный инцидент, и такие пропуски сосредоточены в конкретных категориях и источниках.

## Вопросы и почему выбран именно этот график

| # | Вопрос руководителя | График | Почему он |
|---|---|---|---|
| 1 | Как часто модель соглашается с вердиктом аналитика? | Матрица ошибок словами: «пойман / пропущен / ложная тревога / верно отсеяно» с числами и долями | Четыре клетки понятны без обучения; одна общая «точность» скрыла бы, что ошибки бывают разной цены. Пропуск — красная клетка. |
| 2 | Сколько инцидентов модель пропустит и сколько работы снимет при другом пороге? | Две линии от порога: доля пропущенных инцидентов и доля карточек для аналитиков; ползунок двигает порог на всём дашборде | Это цена решения в одном взгляде: каждая точка — компромисс «риск ↔ нагрузка». | 5 | Можно ли верить «проценту риска»? | Калибровочная кривая: оценка модели против фактической доли инцидентов, пунктир — идеал | Руководителю показывают «риск 70 %» — график отвечает, что за ним стоит на деле. |

## Подробно по вопросам

### 1. Согласие с аналитиком

| | Модель: тревога | Модель: спокойно |
|---|---:|---:|
| **Аналитик: инцидент** | 1 331 — пойман | **335 — пропущен** |
| **Аналитик: ложное срабатывание** | 2 563 — ложная тревога | 11 610 — верно отсеяно |

Решение модели совпадает с вердиктом аналитика в 81,7 % случаев, но эта цифра обманчива: ложных срабатываний в потоке намного больше, чем инцидентов, и модель, которая всегда говорит «спокойно», совпадала бы в 89,5 % случаев. Поэтому важнее другое: из тревог модели реальны только 34,2 %, а 20,1 % инцидентов она не заметила.

### 2. Порог: риск против нагрузки

| Порог | Пропущено инцидентов | Карточек аналитикам | Из тревог — реальные |
|---:|---:|---:|---:|
| 0,05 | 10,3 % | 46,7 % | 20,2 % |
| 0,10 | 13,8 % | 35,9 % | 25,2 % |
| 0,18 (модель) | 20,1 % | 24,6 % | 34,2 % |
| 0,30 | 30,3 % | 16,6 % | 44,3 % |
| 0,50 | 48,8 % | 9,5 % | 56,5 % |

Чтобы пропускать не больше 10 % инцидентов, порог нужно опустить до ≈ 0,03 — но тогда аналитикам уйдёт 53 % карточек вместо 25 %. Пропуска меньше 5 % нельзя добиться ни при каком пороге ≥ 0,01: часть инцидентов модель оценивает почти в ноль. Значит, проблему не решить подбором порога — нужна доработка признаков для «слепых» сегментов (вопрос 3).

### 3. Систематические ошибки

Модель ошибается **не случайно**. Худшие сегменты (только те, где ≥ 10 реальных инцидентов):

| Разрез | Сегмент | Инцидентов | Пропущено | Доля пропусков |
|---|---|---:|---:|---:|
| категория | Управление УЗ | 50 | 47 | 94,0 % |
| категория | Подозрительная активность | 98 | 63 | 64,3 % |
| категория | Вредоносное ПО | 89 | 28 | 31,5 % |
| категория | Атака на инфраструтуру | 204 | 34 | 16,7 % |
| вендор | Microsoft | 58 | 55 | 94,8 % |
| вендор | (не указан) | 1 006 | 264 | 26,2 % |
| вендор | Kaspersky | 29 | 3 | 10,3 % |

Инциденты от событий **Microsoft** модель пропускает почти все (55 из 58), в категории **«Управление УЗ»** — 47 из 50. Это слепые зоны: в обучающих данных таких инцидентов, вероятно, было мало. Пока они не исправлены, карточки этих сегментов нужно отдавать аналитикам независимо от оценки модели.

### 4. Стабильность во времени

Доля пропусков по неделям (недели, где ≥ 5 инцидентов) колеблется от 6 % (неделя с 13.10) до 45 % (неделя с 22.09). Больше 40 % инцидентов модель теряла в неделях с 22.09, 29.09, 06.10. Качество зависит от того, какие атаки идут на этой неделе, поэтому долю пропусков нужно мониторить еженедельно, а не проверить один раз при внедрении.

| Оценка модели | Карточек | Средняя оценка | Реально инцидентов |
|---|---:|---:|---:|

| 5–10 % | 1 710 | 7,6 % | 3,4 % |
| 10–20 % | 2 029 | 13,5 % | 5,9 % |
| 20–30 % | 1 043 | 24,6 % | 14,9 % |
| 30–40 % | 538 | 35,0 % | 30,9 % |
| 40–50 % | 575 | 45,5 % | 24,7 % |
| 50–60 % | 486 | 54,3 % | 34,6 % |
| 60–70 % | 404 | 64,3 % | 45,5 % |

В диапазоне оценок 40–70 % модель **завышает** риск: при оценке около 50 % инцидентом оказывается примерно каждая третья-четвёртая карточка. На краях шкалы (меньше 5 % и больше 80 %) оценке можно верить. Показывать руководству «процент риска» как вероятность без этой оговорки нельзя.

## Прочее

- Модель отвечает быстро: медиана 0,38 с, 95 % ответов быстрее 1,9 с — для советчика в очереди SOC это не узкое место.
- Метрики считаются по размеченным карточкам (`y` = 0 или 1). Решение модели пересчитывается из оценки при выбранном пороге; при пороге модели оно совпадает с полем `y_pred` для всех карточек (проверено в тестах).
- Поля карточки в этом наборе — JSON-массивы (`["MTE_T1053"]`); для разрезов берётся первый элемент.
